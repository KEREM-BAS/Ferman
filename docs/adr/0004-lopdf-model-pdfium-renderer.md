# ADR 0004: lopdf as the document model, PDFium as a read-only rasteriser

- **Status:** Accepted (brief)
- **Date:** 2026-10-14
- **Approval:** brief §3. The read-only open below, Proposed in M0, was approved by the owner on
  2026-10-16.
- **Supersedes:** none
- **Superseded by:** none

## Context

Ferman needs two different things from a PDF library:

1. **A model it fully controls**, for parsing, editing and writing. Editing must rewrite only the
   edited block's operators and leave every other byte identical ([brief §4](../BRIEF.md)). Saving must
   be an incremental update by default ([brief §3](../BRIEF.md)). That rules out any library that
   regenerates page content or rewrites the file on save.
2. **A renderer with high fidelity**, fast enough for the budgets in [brief §5](../BRIEF.md): first
   page visible in under 1 s for a 500-page document, 60 fps scrolling, edit-to-render under 100 ms.
   It must handle the long tail of real-world files: CID fonts, JBIG2 and JPEG 2000 scans, damaged
   cross-reference tables.

The brief fixes the libraries: ferman-core does "parsing/writing (lopdf)" and ferman-render does "page
rendering with pdfium-render", using "prebuilt PDFium binaries (bblanchon/pdfium-binaries) bundled
per platform" ([brief §3](../BRIEF.md)). It also forbids AGPL and non-commercial code: "no MuPDF, no
Ghostscript".

Facts from the dependency check (2026-10-13):

- **lopdf 0.45.0** (MIT). Breaking minor releases come almost monthly (0.41 to 0.45 between June and
  September 2026). Minimum Rust 1.88.
- **pdfium-render 0.9.4** (MIT OR Apache-2.0). Its default PDFium API level is 7881 (`pdfium_latest`
  equals `pdfium_7881`). Its `thread_safe` feature wraps every PDFium call in one global lock, because
  PDFium is not thread-safe.
- **bblanchon/pdfium-binaries**: the newest tag is `chromium/8100`; the tag `chromium/7881` exists and
  matches pdfium-render 0.9.4. Builds are weekly, third-party, unsigned and shared-library only. There
  are plain and V8 (JavaScript) variants.
- **PDFium's licence**: BSD-3-Clause AND Apache-2.0. In the bblanchon archive, PDFium's own text (both
  licences) is `licenses/pdfium.txt`; the top-level `LICENSE` is the packager's MIT notice. The
  `licenses/` folder of the `chromium/7881` archives (checked 2026-10-14) holds 15 files for PDFium and
  its bundled code: abseil, AGG 2.3, fast_float, FreeType (used under the FreeType Licence, not its
  GPL-2.0 alternative), ICU (Unicode-3.0), Little CMS (MIT), libjpeg-turbo (IJG and BSD-3-Clause, two
  files), OpenJPEG (BSD-2-Clause), libpng, LibTIFF, LLVM libc, simdutf and zlib
  ([DEPENDENCIES.md](../DEPENDENCIES.md), section 5.1). No GPL or AGPL code is in the shipped library.

The design adds states that depend on this split: progressive open of a 2,400-page file (a1-7),
password unlock (a1-8, a1-8b), automatic repair (a1-9), an unopenable file (a1-9b), an unsupported XFA
form shown read-only (a11-7c), and document properties with font embedding status (a2-7).

## Decision

### lopdf is the source of truth

- ferman-core wraps lopdf, pinned to `=0.45`. Its optional `embed_image` and `async` features stay off.
- lopdf objects never leave ferman-core. The rest of the engine sees Ferman's own types, so an lopdf
  upgrade touches one crate.
- Every change to a document goes through the model: text edits, organize, annotations, forms,
  signatures. Form field appearances are generated by the engine and written through the model.
  PDFium only draws them.
- ferman-core owns the writer: incremental updates by default and the "optimize and clean" full
  rewrite ([ADR 0008](0008-file-safety-and-saving.md)).
- What lopdf lacks, ferman-core adds and, where it fits, contributes upstream. Known areas to verify in
  M2 and M3: cross-reference repair (a1-9), writing incremental updates into encrypted files with the
  document's own key, and the original cross-reference form (table or stream) in updates.

### PDFium only turns bytes into pixels

- ferman-render uses pdfium-render 0.9.4 with `default-features = false` and the features
  `pdfium_7881`, `thread_safe` and `image_025`. It binds to the library at run time
  (`bind_to_library`) from a path the app passes in.
- PDFium never writes, never saves and never edits. Ferman does not call PDFium's page-editing or save
  functions. After a change, the render thread loads the revised bytes (original bytes plus the
  in-memory incremental update) as a new PDFium document and swaps it in
  ([ADR 0009](0009-threading-and-jobs.md)).
- Ferman's own interpreter builds the text model ([ADR 0005](0005-block-scoped-text-editing.md)).
  PDFium's text functions may be used in tests as a cross-check, never as the model.
- On open, PDFium supplies the page count and page sizes so the first page can render while lopdf is
  still parsing (a1-7). Editing, search and thumbnails turn on when the model is ready. **Approved
  by the owner on 2026-10-16:** if the two parsers disagree on structure (page count or page sizes),
  the document opens read-only with a notice ([ARCHITECTURE.md](../ARCHITECTURE.md) section 5.1).
- Selection, edit marks, search highlights and other overlays are drawn by Flutter on top of the
  tiles. They are never rendered into the PDF.

### Binaries

- We use the **plain (non-V8, non-XFA)** build of bblanchon/pdfium-binaries, tag **`chromium/7881`**,
  for each platform: macOS (arm64 and x64, combined into one universal file), Windows (x64, arm64) and
  Linux (x64, arm64).
- `tools/pdfium` downloads the archives and checks a pinned **SHA-256** per archive before unpacking.
  The hashes are committed. CI fails on a mismatch.
- The libraries are signed with the app's identity when the app is packaged (M5), because the upstream
  builds are unsigned ([Q02](../QUESTIONS.md#q02)).
- PDFium and pdfium-render are upgraded together, in one commit, after the full corpus and pixel-diff
  suite passes on the new pair.

### Licences

- The archive's `licenses/` folder (15 files for `chromium/7881`, including PDFium's own
  `licenses/pdfium.txt`) and the packager's MIT `LICENSE` ship with the app unchanged and appear in the
  third-party notices screen ([G14](../DESIGN_GAPS.md#g14)). The FreeType credit line and the IJG
  statement are included as their licences require.
- The packager's MIT notice (Copyright Benoit Blanchon) ships because it is part of the redistributed
  archive; the packaging scripts themselves are tooling and do not ship.
- The policy and the cargo-deny bans that back this ADR are in
  [ADR 0016](0016-dependency-licence-policy.md).

## Consequences

### Positive

- Full control over bytes: the block-scoped editing rule and incremental saving are possible.
- PDFium's fidelity and speed for rendering, including scans, CID fonts and damaged files.
- Clear licences: MIT, Apache-2.0 and BSD-3-Clause, with attribution-only obligations for PDFium's
  bundled libraries.
- With no V8 in the build, document JavaScript cannot run. That matches the design ("Ferman never
  runs it" in a8-3, "JavaScript blocked" in the a8-4 security report) and the policy the owner
  confirmed in [Q13](../QUESTIONS.md#q13) on 2026-10-16.

### Negative

- **Two parsers, two in-memory copies.** Memory is higher, and the two can disagree on damaged files.
  Disagreement opens the file read-only (approved, above); repair is always a full rewrite to a new
  file.
- **PDFium is not thread-safe.** All rendering goes through one thread
  ([ADR 0009](0009-threading-and-jobs.md)). If M2 measurements show that is too slow, helper processes
  with one PDFium each are the fallback.
- **A PDFium crash ends the app.** C++ crashes cannot be caught. Defences: the pinned binary, fuzzing of
  our own parsers, the recovery journal ([ADR 0008](0008-file-safety-and-saving.md)) and the
  helper-process option.
- **Reload per revision.** Each committed change reloads the document in PDFium. This must fit the
  100 ms edit-to-render budget; it is measured in M3.
- **lopdf churn.** Monthly breaking releases mean deliberate, tested upgrades.
- **No XFA.** XFA-only forms open read-only with an explanation (a11-7c).
- **Optional content (layers).** The layers tab, in M2 ([Q10](../QUESTIONS.md#q10), 2026-10-16),
  needs per-layer visibility at render time. How PDFium exposes optional-content configurations
  through pdfium-render is verified in M2; if it is not enough, the engine sets the visibility in
  the in-memory revision before rendering.
- **Web (P5).** PDFium's WebAssembly build is experimental. hayro is the candidate fallback.

### Follow-up

- M1: `tools/pdfium` with pinned hashes; ferman-render's skeleton render thread loads the library in CI
  and reports its version ([ROADMAP.md](../ROADMAP.md), M1 step 3). Rendering pages starts in M2.
- M2: open, view, tiles, repair path, encrypted files, the two-parser comparison.
- M3: incremental writer, reload-per-edit measurement.

## Alternatives considered

- **MuPDF.** A mature renderer and editor, but AGPL-3.0 (or a commercial licence). Forbidden by the
  brief.
- **Ghostscript.** AGPL-3.0. Forbidden by the brief.
- **Poppler** (and its bindings `poppler-rs`, `poppler-sys-rs`). GPL-2.0-or-later or GPL-3.0, derived
  from xpdf. Incompatible with distributing Ferman under Apache-2.0
  ([ADR 0016](0016-dependency-licence-policy.md)).
- **The `pdfium` crate.** A different PDFium wrapper under GPL-3.0, easy to confuse with pdfium-render.
  Banned in cargo-deny.
- **PDFium as the model too.** PDFium can edit pages, but its content generation rewrites a page's whole
  content stream, which breaks the byte-preservation rule, and it gives little control over how updates
  are written.
- **hayro** (Apache-2.0 OR MIT). A pure-Rust rasteriser by the krilla author. It avoids a native binary
  but does not yet match PDFium's fidelity. Kept as a possible web fallback for P5.
- **Building PDFium ourselves.** Allows static linking and our own signing, but needs Chromium's build
  tooling and a lot of CI time. The brief chooses the prebuilt binaries.
